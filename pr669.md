## Summary
A FlagGems-primary wheel never reaches the software low-precision matrix
path: a generated wrapper is not a route, so on an op the conf leaves on
`none` the FP8 prelude never runs and `torch.mm` goes to ATen's
CompositeExplicitAutograd arm instead -- while `_scaled_mm` stays gated
fail-closed. This PR claims the prelude's matrix ops from `register.cc` on
the platforms that compile it (metax, dcu), and fixes four defects the reach
exposed (bmm rank decoding, `addmm_` keying, `.out`-to-tensor key mapping,
and the hand-back recursing into itself). On bw1100 the suite goes from
`0 passed, 30 failed` to `36 passed, 1 failed` (the one failure is a
FlagGems fp64 `mm` limitation outside this path).

## Problem Analysis

### What was broken/missing?
`tests/integration/ops/test_soft_lowp_gate_dispatch.py` failed 30 of 30 cases
on DCU (`0 passed, 30 failed`), and the same cohort fails on metax in CI.

### Why did it happen?
1. `register_flaggems_dcu.inc` / `register_flaggems_metax.inc` claim exactly
   the conf's FlagGems routes. `mm*`/`bmm*` are `none` in `backends_hygon.conf`,
   so nothing is claimed on PrivateUse1, and the generated wrapper -- the only
   place the `#if defined(FLAGOS_SOFT_LOWP)` prelude lives -- never runs.
2. With the claim in place, four defects inside `soft_lowp/ops.cc` surfaced:
   `DecodeForRoute` decoded `mat2` with the rank-2 helper for a rank-3 `bmm`;
   `addmm_` had no variant entry and asked the `addmm.out` slot by its own key;
   `RunMatrixOut` re-entered `RunMatrix` by the writing key (`mm.out`) and the
   tensor form refused it; and the decoded pair's fallback called this file's
   own wrapper for the plain `mm`/`bmm` key, which is the stack overflow seen
   earlier in this series.

### Investigation process:
Built the tree on bw1100 with `FLAGOS_BUILD_FLAGGEMS=ON`,
`FLAGOS_BUILD_BOXING=OFF`; ran the suite on the vendor python with the build's
`libtorch_fl.so`. Baseline 0/30. Added the claim, then traced each remaining
failure with `--tb=line` and reproduced it in isolation before the next fix.
gdb on the first `mm` confirmed the `.dtype`-slot recursion (fixed in the
base commit of this branch).

## Solution Design

### Implementation approach:
Claim the matrix ops from `register.cc` in the CUDA-ABI `#else` arm, in the
same place and for the same reason the `convolution_overrideable` crossing
exists: neither the conf nor `cpu_fallback` can serve the op, so the claim
follows what the op's route *is* for a low-precision operand.

### Key design decisions:
* The generated FlagGems list is included into the same `TORCH_LIBRARY_IMPL`
  body, and a duplicate `m.impl` is a compile error, so the ops the list
  already names -- metax's `bmm`, `bmm.out`, `addmm*`; DCU's `addmm*` -- are
  guarded out.
* Ordinary operands still take the conf's route inside the wrapper.
* The hand-back skips this file's own `OrdinaryMmKernel`/`OrdinaryBmmKernel`.

### Code changes by file:
* `csrc/aten/register.cc`: the claim, with its rationale.
* `csrc/aten/backends/soft_lowp/ops.cc`: the four fixes.
* `tests/unit/test_conf_registration_consistency.py`: three guard tests (every
  prelude op registered by one of the two lists, the block gated on the
  platform macro, no duplicate with the generated list once the block's
  `#if !defined(<macro>)` guard is honoured per platform).
* `tests/unit/test_soft_lowp_codegen.py`: the `addmm.out` arm now names the
  key the dispatcher answers for.

### Changes by commit:
* `fix: hand an ordinary GEMM to the conf only where the conf's kernel can take
  it` -- `Dispatcher::Fitted` (a key whose answer is this file's own fallback
  is not a route) and the `.dtype`/`.out` key fixes; this is what stops the
  `.dtype`-slot recursion gdb showed.
* `fix: claim the soft-lowp matrix ops on the platforms that compile the
  prelude` -- the claim and the four defects the new reach exposed.
* `fix: guard the FlagGems-routed matrix ops out by name on every platform` --
  a metax-only guard still duplicated the five `addmm*` entries beside
  `register_flaggems_hygon.inc` (Codegen checks, run 40534901451).
* `test: read the gate as code, and accept the generated list as a claim` --
  the new guards counted the block's own comment as a claim and did not credit
  the generated list, which registers the same `Wrapper*` symbols (run
  40536019447).
* `fix: give a decoded matrix pair no route under a key the conf has none for`
  -- a decoded pair was refused the key it was routed by and then handed the
  plain key's slot anyway; the conf is now read for the key before any family
  dispatcher is asked.
* `fix: carry the DCU soft-lowp matrix claim into the conf's route` --
  `backends_hygon.conf` (and the day-0 variant) route `mm`/`bmm` to FlagGems,
  since the claim leaves nothing of these ops to cpu_fallback. This is the one
  route in `gen_vendor_confs.py` recorded as a measured **failure**
  (FlagGems issue #6227: mm hangs on the DCU HCU backend); `none` is the
  alternative and it puts FP8 `mm` back on the in-wrapper computation.
* `fix: keep DCU's mm out-forms off the FlagGems route` -- `mm.out` and
  `mm.dtype_out` (plus the `bmm` spellings on the variant) stay `none`, because
  the FlagGems kernels the Python path reaches for those keys reject dtypes the
  prelude decodes (flag_gems' `mm` raises `CompilationError` on float64; `bmm`
  answered it on the same build).
* `fix: ask the conf, not the dispatcher, whether a decoded key has a route` /
  `fix: read the answer key's route from the conf in one query` -- compile
  fixes found by building the change on bw1100.

### Edge Cases Considered
* Duplicate `m.impl` against the generated list -> guarded, with a unit test.
* Ordinary pair on a `none` route -> hand-back GEMM (the route `none` never
  served on device anyway).
* Flagship FP4 packed operands -> decoded nibble-wise (numerics tests).
* `addmm_` -> routed by the `addmm` key.

### Potential Risks
On a build that routes `mm`/`bmm` to `flagos_python`, the claim now runs the
wrapper before the FlagGems kernel; the prelude's ordinary branch falls
through unchanged, but this is a dispatcher-level ordering change worth a
reviewer's eye. The earlier revert of a comparable claim (#655 -> reverted
`f78ce13`) was for a claim on an op the conf routed `none` without a prelude
to stop the cascade; here the prelude is the reason for the claim.

### Rollback Plan
Revert the commit; the claim block is self-contained in `register.cc`.
